---
title: Migrating from GUT
description: Step-by-step guide to migrating from GUT (Godot Unit Test) to gdtest.
---

**Migration is a single line change for most tests.**

```gdscript
extends GutTest # [!code --]
extends GdTest  # [!code ++]
```

All assertion calls are identical. GDTest's native base class is `GdTest` — it provides the same flat assertion API as `GutTest`, so no other changes are needed for the assertion layer.

## Automated transpiler

gdtest ships a transpiler that handles the mechanical parts of migration automatically.

The commands below use `just`, a command runner (similar to `make`). Install it
from [github.com/casey/just](https://github.com/casey/just), then clone the
gdtest repository to access its `Justfile`.

```sh
# Single file (prints to stdout)
just transpile --source gut my_test_gut.gd > my_test.gd

# Whole directory: rewrite every .gd file in-place
just transpile --source gut test/cases/

# Dry-run: see what would change without writing (exits 1 if any diff)
just transpile --source gut --check test/cases/
```

**The `--source` directory mode rewrites files in place.** Use
`git restore <dir>` or `git checkout -- <dir>` to revert if needed.

The transpiler covers common assertions and lifecycle hooks automatically.
Complex patterns — multi-line method chains, engine error assertions, whole-object
signal watchers — may need manual cleanup; see the API map below.

## What GdTest does

`GdTest` is a thin base class that wraps `Gdt` (the core assertion singleton) with
flat assertion helpers matching GUT's naming. It covers everything most GUT suites
need: assertions, mocking, signal watching, scene helpers, and async waits. There is
no separate compatibility shim for GUT because the surface is nearly identical.

## API differences

| GUT | GdTest | Notes |
|---|---|---|
| `extends GutTest` | `extends GdTest` | The only required change for most suites |
| `await get_tree().process_frame` | `await wait_process_frame()` | |
| `await get_tree().create_timer(t).timeout` | `await wait_physics_seconds(t)` | |
| `gut.p("...")` / `gut_print(...)` | `print(...)` | |
| `before_all()` | `GdtFixture.before_suite()` | Available through a fixture plugin |
| `after_all()` | `GdtFixture.after_suite()` | Available through a fixture plugin |
| `autofree(obj)` | `autoref(obj)` | Same cleanup intent, renamed helper |
| `double(script)` | `mock(script)` | Same main use case |
| `partial_double(script)` | `partial_mock(script)` | Same caveat |

## Things to check

**1. Autoload state leaks within a file**

Under `--isolation=file` (default), one Godot process serves all tests in a
file. Tests that mutate global singletons (`GameClock`, etc.) need
`--isolation=test` to get a fresh process per test.

**2. Signal lambda parameter count**

GDScript 4 does not silently drop extra signal arguments. A signal with 3
parameters must be connected with a lambda that accepts all 3:

```gdscript
# Wrong - crashes in GDScript 4
node.my_signal.connect(func(): ...)

# Correct
node.my_signal.connect(func(_a, _b, _c): ...)
```

## Critical migration gaps

### Hard gaps

- `assert_engine_error(...)` and `assert_engine_error_count(...)` do not have a pure-GDScript equivalent in `gdtest`. GUT hooks the engine error channel; `gdtest` does not.
- `watch_signals(obj)` has no whole-object watcher equivalent. `gdtest` requires one `watch_signal(obj, sig)` per signal.

### Medium gaps

- `assert_push_error(...)` and `assert_push_warning(...)` only observe `Gdt.push_error()` and `Gdt.push_warning()`. Existing production code using native `push_error()` or `push_warning()` must be adapted if those assertions matter.
- `before_all()` and `after_all()` move into a `GdtFixture` plugin via `before_suite()` and `after_suite()`.
- Multiple-process-frame waiting is manual because `wait_process_frame()` only exposes a single frame at a time.

### Small gaps

- Some GUT convenience helpers collapse into inline expressions.
- Negative file assertions and suite pass/fail bookkeeping helpers are not first-class APIs.

## Migration effort by pattern

| Pattern in the GUT suite | Expected effort |
| --- | --- |
| Mostly `assert_eq`, `assert_true`, `assert_null` | Trivial |
| Named-signal assertions | Low |
| Mock-heavy tests | Low to medium |
| `before_all` or `after_all` setup | Medium |
| `simulate(...)`-driven tests | Medium |
| Engine error assertions | High |
